# M4.1 Trip Polls Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a server-authorized, single-choice Trip Poll feature with safe database invariants, realtime refetch, responsive UI, and focused verification.

**Architecture:** PostgreSQL owns Poll lifecycle, authorization, and vote integrity through additive tables and RPCs. Next.js Route Handlers expose a thin aggregate read/mutation API, and a dedicated Poll workspace uses the existing Trip-scoped SSE bridge to refetch authoritative state after Poll events.

**Tech Stack:** Next.js 16 App Router, React, TypeScript, Supabase PostgreSQL/RPC/Realtime, Vitest, Playwright.

## Global Constraints

- Do not modify applied M1–M3 migrations or begin M4.2.
- Keep Soft Identity and the existing server authorization boundary; do not add Supabase Auth or custom JWTs.
- Polls are single-choice, text-only, Trip-scoped, and non-anonymous.
- Closing is one-way; closed Polls remain readable and preserve options/votes.
- Poll creator and Trip Owner may close/delete; other members may not delete another creator's Poll.
- PostgreSQL/API is the source of truth; realtime only triggers authoritative refetch.
- Ask once for remote application of `supabase/migrations/20260925135634_m4_1_trip_polls.sql` after local verification.
