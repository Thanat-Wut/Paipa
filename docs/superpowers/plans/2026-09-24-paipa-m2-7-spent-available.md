# PAIPA M2.7 Spent & Available Balance Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Extend the existing M2.5 money summary with exact, authorized, database-derived Trip Fund spending and available balance, then verify the complete M2.7 behavior against the real Supabase-backed API.

**Architecture:** Keep `public.get_trip_money_summary(uuid, uuid)` as the single read RPC and replace its definition in a new additive migration. Calculate payments and active Trip Fund expenses in separate aggregates within the same SQL statement, subtract with PostgreSQL `numeric`, and return canonical decimal strings. Extend the existing parser and real API test coverage without introducing persisted totals, a competing read model, expense mutation changes, or Money UI.

**Tech Stack:** Next.js Route Handlers, TypeScript, Supabase PostgreSQL / SQL migrations, Supabase Storage, Vitest, Playwright, Supabase MCP.

## Global Constraints

- `Collected = SUM(payment_submissions.amount) WHERE status = 'verified'` and includes verified payments from historical/former contributors.
- `Spent = SUM(expenses.amount) WHERE payment_source = 'trip_fund' AND deleted_at IS NULL`.
- `Available = Collected - Spent`; calculate using PostgreSQL `numeric`, never JavaScript `number`, and allow a negative result.
- Return money values as decimal strings with two fractional digits; zero is `"0.00"` and a negative example is `"-500.00"`.
- Extend `get_trip_money_summary`; do not create a second summary RPC, aggregate table, persisted counters, triggers, or split-bill logic.
- Preserve M2.5 Expected, Pending, Collected, contribution formulas, authorization, receipt permissions, and one-statement snapshot behavior.
- Count `member_refund` when `payment_source = 'trip_fund'`; exclude personal, soft-deleted, and superseded historical expense rows.
- Add a new migration; do not edit applied migrations through M2.6.
- Do not begin full Money UI / M2.8. Do not change M2.6 expense mutation behavior.
- Run `npm run lint`, `npm run typecheck`, `npm test`, `npm run test:e2e`, `npm run build`, and `git diff --check`; verify SQL M2.1–M2.7 and runtime M1, M2.3–M2.7 where runnable.
- Clean every test fixture created by the run, including app rows and Storage objects. Do not delete unverified data.
- Commit separately as `feat: add M2.7 spent and available balance`; do not push.
