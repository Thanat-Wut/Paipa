# M2.7 spent and available read model

`public.get_trip_money_summary(p_actor_id uuid, p_trip_id uuid)` keeps its M2.5 signature, `jsonb` return type, `language sql`, `stable`, `security invoker`, and empty search path. Only `service_role` may execute it. The existing authorization CTE admits a profile that owns the trip or is a current trip member; a former member and an outsider receive no row.

The result preserves `currency`, `budgetPerPerson`, `expected`, `pending`, `collected`, and `goingCount`. It adds:

- `spent = sum(expenses.amount)` for rows in this trip whose `payment_source = 'trip_fund'` and `deleted_at is null`, with zero when no rows qualify. Category does not narrow this sum, so an active `member_refund` counts. Personal expenses, soft-deleted rows, and a replaced parent that was soft-deleted do not count; an active replacement child does.
- `available = collected - spent`. This remains signed: overspending produces a negative value.

Both new amounts are rounded to two places and returned as decimal text, matching the existing totals. PostgreSQL `numeric` arithmetic preserves exact cents, including `0.10 + 0.20 - 0.15 = 0.15`.

The SQL statement retains independent `payment_totals` and `expense_totals` CTEs over the same `authorized_trip`. It does not join raw payment rows to raw expense rows, which would multiply both sums. The single stable SQL statement reads a single PostgreSQL statement snapshot, so `collected`, `spent`, and `available` describe one database state.

## Measured expense aggregation plan

On the dedicated test project, a rollback-only fixture inserted one trip and ten `trip_fund` expenses. The measured query was:

```sql
explain (analyze, buffers)
select coalesce(sum(e.amount) filter (
  where e.payment_source = 'trip_fund' and e.deleted_at is null
), 0::numeric) as spent
from public.expenses e
where e.trip_id = 'e71a3bcc-712e-4a10-b8ec-33ce1031e67a'::uuid;
```

The planner chose `Aggregate` over a `Seq Scan` filtered by `trip_id`, scanning ten rows with two shared buffer hits. Planning took 0.174 ms and execution 0.076 ms. A sequential scan is reasonable at this fixture size. The existing M2.6 `expenses_trip_spent_at_idx` begins with `trip_id`; the unique `(trip_id, id)` index and `(trip_id, created_by, client_request_id)` index also support trip-scoped lookup. There is no measured evidence for an additional index, so M2.7 adds none. A larger production data distribution would need its own plan measurement before an index decision.
